# 手柄输入与机器人控制接口改写工作报告

编制日期：2026-10-21。

**项目：Hand Tracking Streamer**

依据：项目历史任务《用手柄重写软件》及当前 Unity/Python 源码。本文记录输入端改写和操作流程；机器人执行端的完整闭环不作为已经验收的成果。

## 1. 工作背景与目标

原 HTS 以手势追踪为主要输入，输出手腕和手指关键点。最初需求是通过 Quest 手柄提供更直接的手部控制目标。随后需求演进为：保留头部、上半身和真实手指数据，同时加入左右手柄位姿，用摇杆控制移动、朝向和高度。最终明确取消下肢推测与可视化，由机器人端自行设计腿部姿态和行进逻辑。

因此当前正式模式是 `Full Hands + Controllers`，不是最初设想的纯手柄软件。代码沿用原工程并扩展输入链路，没有证据表明另建了一个独立控制产品。

## 2. 开发过程与关键决策


| 阶段       | 实施内容                                                  | 当前结果                 |
| ---------- | --------------------------------------------------------- | ------------------------ |
| 手柄输入   | 读取左右 Touch 的位置和四元数，复用原网络设置             | 保留                     |
| 双输入并存 | 为手柄新增`controller_wrist` 标签，避免覆盖真实 `wrist`   | 保留                     |
| 摇杆移动   | 新增统一 locomotion provider，积分得到位移与 yaw 偏移     | 保留                     |
| 跟随修复   | 头、手、手柄、body 使用同一偏移来源                       | 保留                     |
| 高度控制   | 右摇杆 Y 设置竖直偏移及上下限                             | 保留，输出目标高度       |
| 下肢尝试   | 曾尝试程序化腿部、root 补偿和 BodyDataAsset.Root modifier | 后续撤回，不作为当前功能 |
| 模式收敛   | 界面只保留 Full Hands + Controllers                       | 保留                     |
| 职责收敛   | 84 关节改为 70 个上半身关节，关闭 foot 流                 | 当前正式方向             |

历史上“机器人平移但没有正常迈步”和“蹲起没有实现”的反馈说明：移动输出坐标并不能自动生成机器人步态。之后用户明确要求自行设计腿部，当前实现遵循该决定。

## 3. 当前数据链路

```text
Quest 头显、真实手部、左右手柄
    ↓ Unity / Meta 数据源
Head / Hand / Body / Controller streamer
    ↑ JoystickLocomotionProvider 提供统一偏移
    ↓ TCP 或 UDP 文本数据
电脑监听、可视化、Body 数据录制
    ↓ 后续需要明确接入的机器人适配层
坐标标定、目标选择、重定向/IK、步态控制 → MuJoCo
```

这里的 TCP/UDP 数据是人体或手柄目标，不是机器人关节力矩，也不是已经定义好的 ROS 控制话题。现有监听脚本可以继续作为诊断工具，但不能仅凭可视化运动就确认模拟机器人已经受控。

### 4.1 手柄坐标与数据格式

```text
Left controller_wrist:, x, y, z, qx, qy, qz, qw
Right controller_wrist:, x, y, z, qx, qy, qz, qw
Left wrist:, x, y, z, qx, qy, qz, qw
Right wrist:, x, y, z, qx, qy, qz, qw
Body root:, x, y, z, qx, qy, qz, qw
Body joints_pose:, [x, y, z, qx, qy, qz, qw] × 70
```

前两项是手柄；后面的 wrist 是真实手势追踪。调试模式可能在标签中附带帧号和时间。位置采用 Unity 空间；四元数顺序为 xyzw。手柄有 trackingSpace 引用时转换为世界位姿，找不到引用时回退为本地追踪位姿，因此必须检查 Camera Rig 引用，不能无条件认为所有来源处于同一空间。

“模式允许同时发送”不代表戴着手柄时手指必然有效。当前 Scene 中 `launchSimultaneousHandsControllersOnStartup` 为 0，项目脚本未发现显式启动该并发能力的调用；具体设备运行时是否同时提供有效手部与手柄数据需要实测。

### 4.2 摇杆映射与参数


| 输入/参数    | 当前代码默认值或行为          |
| ------------ | ----------------------------- |
| 左摇杆 X/Y   | 沿参考朝向的地面右/前方向移动 |
| 右摇杆 X     | 累加 yaw 偏移                 |
| 右摇杆 Y     | 累加 Unity Y 轴高度偏移       |
| 平移速度     | 1.0 单位/秒，通常按米理解     |
| 高度速度     | 0.6 单位/秒                   |
| 高度偏移限制 | -0.6 至 +0.4                  |
| 转向速度     | 90 度/秒                      |
| 死区         | 0.15                          |

上述为脚本默认值，场景中序列化 Inspector 值可覆盖它们。输入仅在推流状态更新；移动方向优先使用指定 reference，否则使用主相机方向投影到地面。

核心计算为 `position_out = position_in + PositionOffset`、`rotation_out = yawRotation * rotation_in`。当前没有将所有关节位置绕统一 root 旋转，也没有在 provider 中抵消真实人体位移。因此右摇杆 yaw 不是完整刚体转身；高度偏移也不是已经求解好的弯膝或足底接触动作。对机器人接入应保留这个区分。

## 5. 详细操作：Unity 与 USB 连接

1. 在 Unity 打开上述场景，等待脚本导入结束，先处理 Console 中的编译错误。
2. 检查 Camera Rig、trackingSpace 与左右手部数据源引用。Body streamer 应挂在带 `Body`/`IBody` 组件的对象上，只保留一个 Body streamer。
3. AppManager 会在运行时补建手柄 streamer 和 provider；不要因为编辑态没有看到运行时对象就重复添加。若手动配置 provider，检查速度、死区和高度范围。
4. 保持正式输入模式 `Full Hands + Controllers`。当前不需要恢复历史 controller-only 过渡选项。
5. 连接 Quest，允许 USB 调试。电脑执行：

```bash
adb devices
adb reverse tcp:8000 tcp:8000
adb reverse --list
```

设备应处于 `device` 状态，映射列表应包含 8000。ADB reverse 只转发 TCP，不用于 UDP。

6. 先启动电脑接收端：

```bash
python scripts/visualizer.py --protocol tcp --host 0.0.0.0 --port 8000 --show-fingers
```

7. Unity Android Build Profile 中确认包含当前场景，然后 Build And Run 到 Quest。测试设备上实际安装的新 APK，不要仅修改 Editor 后继续运行旧 APK。
8. Quest 应用填写 TCP Wired、IP `127.0.0.1`、端口 `8000`，点击 Start Streaming。
9. 确认上半身、头部与左右控制器标记出现，再开始动作测试。手指不可见时同时检查追踪有效性和 `--show-fingers`，不要把缺手指当作手柄链路整体故障。
10. 结束时停止推流；代码中左手柄菜单键也调用 StopStreaming。它停止数据发送，不等同于机器人硬件急停。

## 6. 逐项动作验收


| 操作           | 应观察到的输出                     | 判断范围                 |
| -------------- | ---------------------------------- | ------------------------ |
| 只移动左手柄   | 左 controller_wrist 改变           | 手柄读取与网络           |
| 只移动右手柄   | 右 controller_wrist 改变           | 左右标签正确             |
| 转头、点头     | 头部方向标记变化                   | 头部旋转链路             |
| 推左摇杆       | body、头、手柄位置共同平移         | 统一偏移是否应用         |
| 推右摇杆上下   | 输出竖直位置变化，达到限值停止累加 | 目标高度控制             |
| 推右摇杆左右   | 四元数出现 yaw 偏移                | 不能据此验收完整骨架转身 |
| 释放摇杆       | 不再继续积分，已积累位置保留       | 死区与积分               |
| 停止后重新推流 | provider 偏移重置                  | 软件会话重置             |

若 body 与手柄分离，检查是否运行同一版本 APK、所有 streamer 是否找到同一 provider、trackingSpace 引用是否一致。不能只修改 Python 绘图掩盖发送端空间不一致。

## 7. 无线连接与原始数据检查

无线时电脑与 Quest 应能互相访问；电脑端仍绑定 `0.0.0.0:8000`，Quest 的目标 IP 改为电脑实际局域网 IPv4，而不是 `0.0.0.0` 或 Quest 自己的 localhost。选择 TCP WiFi，并显式填入同一端口。

要检查原始文本，先停止占用 8000 的 visualizer，再运行：

```bash
python scripts/sockets.py --protocol tcp --host 0.0.0.0 --port 8000
```

换回可视化前停止该监听器并重新开始 Quest 推流。多个独立脚本不能同时绑定相同监听端口；需要可视化加录制时使用组合脚本。

UDP 可采用以下接收命令，Quest 填电脑实际 IP、UDP、9000：

```bash
python scripts/visualizer.py --protocol udp --host 0.0.0.0 --port 9000
```

## 8. 录制和回放

```bash
python scripts/record_visualize_body_stream.py --protocol tcp --host 0.0.0.0 --port 8000 --duration 20 --expected-joints 70 --show-fingers -o recordings/controller_body_test.npz
python scripts/replay_body_recording.py recordings/controller_body_test.npz --speed 0.5 --loop
```

两条命令依次运行。第一条结束保存后，第二条可脱离 Quest 回放。建议分段测试静止、左右手柄、平移和高度。

重要限制：现有录制器保存的是 Body root/joints，并不完整保存独立 `controller_wrist`、原始摇杆轴值和全部网络消息。组合脚本虽可实时显示控制器，生成的 NPZ 仍不是完整手柄会话记录。若需精确重放手柄驱动策略，应另扩展带时间戳的控制器与摇杆日志。

## 9. 与 Docker/MuJoCo 的下一步接口

保留监听模块作为采集入口，明确“机器人末端目标使用 controller_wrist 还是真实 wrist”，随后进行起始姿态标定、Unity 到机器人坐标变换、尺度及可达范围映射，再由机器人端求解双臂姿态和腿部控制。若原监听器继续占端口，机器人桥接应从监听器转发后的通道取数据，不能另抢同一个端口。

当前偏移已经写入目标位姿，机器人端不要再重复叠加一遍。后续若改为发送独立速度/高度命令，应明确协议版本。机器人视频回传属于相反方向的数据通路，启动视频服务本身不会自动建立控制桥接。

## 10. 工作成果与验证范围

本阶段形成了手柄位姿输入、手势/手柄独立标签、统一摇杆偏移、精简上半身可视化及单一正式模式。历史对话记载了 Python 语法检查及部分 Unity 编译/日志检查；本次报告核对了当前源码与历史记录，没有重新连接 Quest、构建 APK 或实测机器人运动。

因此可确认的是输入端与数据接口实现；真实手指和手柄并发、机器人重定向、步态、蹲起及端到端时延仍需分别验证。
